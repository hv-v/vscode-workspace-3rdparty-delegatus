Speed Enforcement
As explained in Evidence Rules Management (Enforcement Manager), the Speed Enforcement node, receives and process the events from Evidence Rules Manager to check the configured speed rules. Evidence Rules Manager performs the management of the evidence and uses the service to request for speed rules to be applied to the received detection.

Speed Enforcement will need to support the following functionalities:

Check the speed against the limits and rules for vehicle class with location-dependent configuration provided by operational profile service.
Receives information from speed limit and validity from VMS validator and keeps an history of VMS information.
Responsible for merging standard speed limits (from configuration) with VMS limit information and checking the speed.
Shall be possible to configure uni-directional measurement of speed checking (for markets that for each camera only allow speed measurement in one direction).
Must connect to operational profiles component to get the conditions for the scheduled operation, if defined.
Configurable grace period for changing speeds (either by VMS or operational profile schedule).
Shall report if the speed is below a minimal speed limit or above a maximum. This is to report and be used as information in the databar. (e.g. for PTB release, it shall display "< 10 km/h" or "> 300 km/h" where appropriate).
Speed Enforcement shall be capable of reading a configuration covering the above functionalities and apply the rules to the event received. After checking, returns the information if the vehicle is above or under the speed limit defined for the vehicle (e.g. depending on the lane, class,...). This configuration will be specific to the market/client, so needs to be easy to make the configuration at setup. A possible example configuration is presented below:

spot_speed_rules_uk_wales.yaml


version: 1

id: "highway1"
name: "Fast highway"
country: "UK"
region: "Wales"
default_unit_system: "METRIC"        # or "IMPERIAL"

SpeedConditions:
  - enabled: true
    lanes: ["1", "2", "3"]
    direction: "TOWARDS"             # "BOTH"; "TOWARDS"; "AWAY"
    base_speed_limit: 120        
    trigger_speed_limit: 130
    vehicle_class: [car, truck]  

  - enabled: false
    lanes: ["4"]
    direction: "BOTH"               # "BOTH"; "TOWARDS"; "AWAY"
    base_speed_limit: 80        
    trigger_speed_limit: 90
    vehicle_class: [car, truck]   

Operational profiles are handled by a different process that will evaluate the configured schedule for the enforcement and set the profile with the specific speed limits to be applied in Speed Enforcement. Although this going to be detailed on a separated page for Operational Profiles, regarding the diagram above, Operational Profile block will make the configured profiles available for Speed Enforcement and whenever a new event is received, Speed Enforcement will request Operational Profile to indicate which profile shall be used for the given timestamp (which can be in the past or future). Note that it will always exist a default profile with the speed limit definitions that is used in case no other is defined.

For prediction triggers, it will be requested with a timestamp to operational profile manager, the speed limit and rules to be applied for that time period. Operational profile manager will determine the active profile and can also include a small switching history to be used for grace period analysis. When the actual trigger is received, it is checked again when sending for post-validation. 

Speed events needs to include all the required metadata for speeding violation documentation (reference: SHIRE-344 - Authenticate to see issue details ), which includes for example, the local speed limit at the time of the measurement, trigger limit at the time of the measurement and travel speed. With that information, Evidence Rules Manager, in case of an offence, will create the evidence with the speed violation. Besides that, the information needs to be analysed to report other events, like values outside pre-defined ranges that needs to be reported to the user using evidence_status topic (e.g. speed below 10 km/h, reference: SHIRE-346 - Authenticate to see issue details ).

Another important topic is when we have an event that doesn't have a rule associated the operator needs to be notified. For example, considering the possible configuration above, if we have a vehicle going in lane 1 on away direction, the operator needs to be notified by an evidence_status message (see Evidence Rules Management (Enforcement Manager) of the event.
