# Implement first iteration of jen_calibration_manager

#### Objective

We need a bridge between ROS calibration config parameters and related the ROS messages.

ROS parameter for (fixed) calibration data (will be enhanced with meta data and protected later):
camera intrinsics <–> msg/CameraInfo Documentation?
camera to lidar extrinsics <–> msg/TransformStamped Documentation
 ROS alignment data
lidar to scene extrinsics <–> msg/TransformStamped Documentation
 

#### Tasks

Implement the relay node as calibration manager
Implement the transformation of ROS intrinsic and extrinsic parameters to dedicated ROS messages. This must be done at node startup and at runtime, when the ROS parameter changes.
Make sure that the implementation is generic so that we can handle the (fixed) calibration data from SR355 and calibration data from Specs 5.
I think we need to remove the camera intriniscs parameters from the camera driver node. -> covered by SHIRE-1661 jen_sc_camera_driver: Remove node parameter 'calib' - Jira SMS
Implement a first basic validation: are the frame_id consistent and well-formed?
If validation fails, a dedicated node monitoring state must change. The message shall contain the fail reason. We can discuss later, how this can be translated.
The new monitoring events shall be added to our diagnostics aggregation
For SR355:  We need a way to store changed road-to-falcon extrinsics at runtime. Rest is fixed.
For Vector: All extrinsics can change?
For the first iteration, provide a service to update non-static transformations, like "SetTransformation".
We want to be able to update single transformations with this service.
Calibration manager must merge it with existing non-static transformations and create a full YAML over all non-static transformations.
Call the config manager setNodeParameters service with this YAML
Receives the config manager response
 

#### Acceptance criteria

Calibration and alignment data is loaded
Validation rules are implemented.
 

#### Notes

Validation rules SR355 PTB ( a starter):

Check valid rotation matrix values (all values from -1 to 1, orthogonality, determinant is +1, ...)
Check valid intrinsics values (focal length > 0, matrix determinant > 0, principal point near image center, skew coefficient should be near zero)
know frame_ids of our sensors, verify that we have the transformations defined.
We don't need the flexibility of transformation chains.
We configure fixed the transformation paths, like (road–>lidar after alignment), lidar–>camera1, camera1–>camera2.


# 1395 How to store and provide calibration data? Linked with 1619

##### Comments: 

My assessments

Calibration data (extrinsics, intrinsics) is configuration data that has to be handled mostly as other config data:

Calibration data is writable before and read-only after homologation. Values are unique per device.
Calibration data ist stored in a separate configuration file, though.
Road-to-sensor transformation configuration is writable as it is learned during alignment.
Config Manager shall load and verify this data as any other config data.

After loading, we decided for good reasons that the extrinsics part of the calibration data shall not be provided as normal ROS parameters to the nodes (which would be possible), but wanted to publish it as tf2 transformations.

So we need a process that reads the extrincs config data and publishes it as tf2.
This functionality could be a feature addition to the config manager. It could be a specific node.

It should not be the jen_lidar_tracker. Other sensors need extrinsics as well. Therefore, publishing tf2 must be in the generic system area, e.g., in config manager.
